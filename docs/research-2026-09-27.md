## Verdict: continue. Do not abort. Measure before building more.

**The technology choice is right.** Vector-first matching of CAD-exported
PDFs with an OpenCV raster fallback, a learned verifier over user
corrections, and an LLM only for legends and ambiguous crops is the
architecture every independent line of evidence points to (symbol-spotting
literature, the FloorPlanCAD/VecFormer family working on vector primitives,
P&ID work using VLMs as judges, and what the commercial tools ship). The

## What the external research adds to `docs/improvement-review.md`

### 1. Market position (decides *what* Pinny should be for)

Receptacle counting with a review UI is a solved product category:
Countfire (~$1.2K/user/yr), Kreo Pro (~$2.1K), Togal (~$3.6K), STACK (~$3K),
Drawer AI ($1.8–3.6K), Beam AI (~$17K done-for-you), and Trimble Accubid
now ships LiveCount AI natively. Bobyard raised $35M and launched
electrical in June 2026. **Pinny cannot win on "faster takeoff for
estimators"** and should not try.

What no vendor offers, and where Pinny is a genuine differentiator:

* pins embedded in *your* QC workflow through an API you control (Kreo's
  API is architectural-only; Togal, Beam, Bobyard and Trimble have no
  detection API);
* data ownership and per-project learning from your own reviewers'
  corrections (vendors retain data and don't learn your standards);
* cost at scale once seats exceed roughly ten.

API-first engines that could replace the raster/learned tiers if they pass a
benchmark on *your* sheets: Bedrock (bedrock.cv), Sparkel (API + MCP,
€129/mo), Nomic Drawing Parse. None publishes electrical-symbol
precision/recall. Run them through the same 20-sheet benchmark as Pinny and
decide on numbers.

Estimator complaints about every existing tool, which are Pinny's
opportunity if it handles them and its failure mode if it doesn't: counting
symbols inside legends, details and schedules; legend drift job to job;
double counts between enlarged plans and base plans; scanned/marked-up
sheets; near-identical symbols distinguished only by text (GFI vs duplex,
USB); "the count is never 100%" so everything is reviewed anyway.

**Recommendation:** position Pinny as the **QC count / revision-diff /
data-ownership** tool first. Treat estimating as a buy-or-defer decision at
Gate B (below); the estimating use case needs multi-symbol scanning,
legend-driven symbol discovery, area bounding, counts export and assembly
mapping, none of which exist yet, and the vendors above already have them.

### 2. Vision LLMs (confirms the head's opt-in-only stance)

Evidence through 2026 is consistent that VLMs are weak at dense counting and
precise localisation: best VLM ≈0.53 counting accuracy on UNICBench;
document-grounding IoU ≈14% on MMDocBench; HoloCount finds top models
"degrade significantly" on dense counting; Anthropic's own vision docs say
localisation is approximate and counting many small objects is unreliable.
A 7200×4800 sheet sent whole to Claude is downscaled ~2.8× (long edge 2576
px on Opus 5 / Sonnet 5 / Fable 5.1), so a 15 px receptacle becomes ~5 px.
Tiling costs ~55–70K tokens per sheet and still loses to OpenCV.

Where Claude pays off, per 100-sheet set:

| Task | Model | Cost |
|---|---|---|
| Legend / symbol schedule → structured JSON, once per set | Opus 5 | ~$0.10 |
| Ambiguous-crop adjudication (only the uncertain score band), batched | Sonnet 5 via Message Batches | ~$5–17 |
| Title block / sheet index | Sonnet 5 or Haiku 4.5 | ~$0.50 |
| Full-sheet detection or counting | none | — |

`docs/improvement-review.md` Phase 3 already specifies this. Nothing at head
calls an LLM yet; that is fine and should stay opt-in and keyed.

### 3. Detection literature (confirms the head's tiers, one correction)

* Rezvanifar et al. found simple clutter-tolerant correlation beat graph
  methods on floor-plan symbol spotting and that **precision, not recall, is
  the usual weak spot** (legends, callouts, schedules). The head has blur,
  mirroring and symmetry handling but **no legend / title-block / schedule
  masking**. That is the highest-value small addition left in the raster
  tier, and it is what estimators complain about most.
* SkeySpot/DELP: YOLOv8 on 45 electrical plans reaches 97% mAP@50 for double
  sockets but fails on classes distinguished only by text. Rule of thumb:
  ~50–100 confirmed boxes per class across ≥10 sheets before a learned
  detector beats the template baseline. The Phase 2 promotion gate is the
  right mechanism; it needs real labels to be meaningful.
* Visual-prompt foundation models (T-Rex2/DINO-X, CountGD++, SAM 3,
  Rex-Omni) have no published results on 25 px line symbols; zero-shot
  Grounding DINO scores ~0% on thin floor-plan symbols. Worth a spike on
  scanned sheets only.
* Correction to the reviews: the head correctly uses pypdfium2/pikepdf.
  Keep it that way; PyMuPDF and Ultralytics YOLO are AGPL, as
  `docs/improvement-review.md` already notes.

### 4. Integration with the QC app

The viewer's Starlette API is the integration surface. Keep the shape:
library core + one long-running service process in front of SQLite, JSON
over HTTP, `PinnyError → 4xx {error:{code,message}}`. The secure web tier
(Step 3) already solves reviewer identity, roles and deletion. Remaining
gaps by use case:

| Need | QC | Estimating |
|---|---|---|
| Revision diff between two `document_version`s of a sheet (reuse the evaluator's matcher) | **required** | nice |
| Legend/title-block exclusion regions | required | **required** |
| Counts export (CSV/Excel per sheet, per symbol) | nice | **required** |
| Multi-symbol-type scan in one pass, legend-driven symbol discovery | nice | **required** |
| Room/area bounding | nice | **required** |
| Circuit/homerun tagging (text from PDF on vector sheets, OCR on scans) | — | later |

Data: customer drawings are the engineer of record's copyrighted work and
crops are derived works. Keep everything inside the project boundary, keep
the deletion path, and get written permission before training across
customers.

## Plan: measure, then gate

**Weeks 1–2 (one owner, no new modules).**
1. Pick 6 real sheets from ≥2 drawing sets (at least one scanned). Label
   blind, two people, per `evaluation/README.md`, with symbol class and
   exclusion regions (legend, details, schedules) recorded as geometry.
   Use the viewer to place points; do not label in GIMP.
2. Run I1–I8 on the integrated app and record results in
   `INTEGRATION_CHECKS.md` (date, commit, command, output path).
3. Run `pinny.benchmark run --modes template,template+verifier,model` on
   those pages as a real test split and `promote-report`.
4. Run the same sheets through Bluebeam VisualSearch and one API engine
   (Bedrock or Sparkel) so the comparison is on numbers.

**Gate A (end of week 2).** Tolerance fixed beforehand (half the symbol
diameter at 200 DPI, ~10–15 px). Same-sheet exemplar.
* recall ≥ 90% on ≥ 4/6 sheets → continue to Gate B work;
* 70–90% → next work is legend masking and vector-tier coverage only;
* < 70% → stop building; decide vector-only, API engine, or abort.

**Weeks 3–6.** 12 sheets across 4 sets, cross-sheet exemplars, legend
masking, revision diff for QC. Retrain the Phase 2 models on real labels
and run the promotion gate.

**Gate B (week 6).**
* QC: recall ≥ 95%, precision ≥ 80% → wire into the QC app.
* Estimating: recall ≥ 97%, precision ≥ 85% (a 5% undercount on 500
  receptacles is ~25 devices × NECA labour + material, straight off margin;
  estimators already hit 1–3% by hand). Below this, estimating is buy or
  defer, not build.
* **Abort** if recall is still < 80% after legend masking and the vector
  tier on your real sheets, or if a commercial product meets the QC need
  inside your price ceiling.

## Process notes

The session-per-module, contracts-first pattern in `docs/agent-ownership.md`
is 2026 best practice and has clearly worked here (Phase 1 and 2 integrated,
CI, one test runner). Two things to keep it that way:

* Add a short `CLAUDE.md` (< 40 lines): install/test commands, "you own
  only the paths in `docs/agent-ownership.md`", "never edit
  `docs/contracts.md` or `pyproject.toml` without the coordinator", "never
  commit drawings, databases, crops or exports". The repo has none, and each
  new session re-derives this.
* Set the GitHub default branch to the integration branch. It is currently
  `claude/great-cerf-hbzlrf` (2026-09-23), which is what a fresh session
  clones and is 20+ commits behind; this review's first pass audited that
  stale snapshot.
* Scope check on the training site: Steps 4–7 (jobs sandbox, deployment,
  training API and pages) are real work for a 3-user team and none of it
  changes the Gate A answer. Sequence it after Gate A.
